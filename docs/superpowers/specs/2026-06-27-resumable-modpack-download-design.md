# Resilient, resumable modpack downloads — design

Date: 2026-06-27
Status: approved (pending spec review)
Repos touched: `TechnoparkLauncher` (client) and `GamesGlitchlessStatic` (server static generator)

## Problem

A GTNH ("NewHorizon") install is ~12,044 files. A real user log
(`technoparklauncherlog 20260627`) shows **8,130 of 12,044 files failing** with
`ConnectTimeoutException`, after which `IncrementalDownloader.download()` aggregates
the failures and **throws**, so the changelog timestamp is never persisted. On the
next launch the whole window is recomputed from `lastUpdate = 0` and **every file is
re-downloaded from scratch**, hitting the same wall — the user is permanently stuck.

Two independent root causes:

1. **Self-inflicted connection storm.** `Dispatchers.IO.limitedParallelism(8)` bounds
   *threads*, not *in-flight suspending I/O*. ktor downloads suspend on the network and
   release their thread, so all 12k requests launch at once and overwhelm the connection
   pool → mass connect timeouts. (Fixed already; see commit `40ef16c` on this branch.)
2. **No resume / no convergence.** `buildDownloadPlan` enqueues every `ADD`
   unconditionally — it never checks whether the local file is already correct. Combined
   with timestamp-only-on-full-success, any partial failure discards all progress.

## Goals

- The download **resumes**: a re-run fetches only missing/incorrect files, never the
  whole pack again.
- Every downloaded file is **verified** against a server-provided hash; corruption is
  detected and re-fetched, not silently kept.
- A flaky network finishes in **one launch** where possible (bounded in-run retry).
- The user can **tune parallelism**; default is the CPU core count.
- **Cheap per-launch update check**: an unchanged changelog costs a 304 (no body), and a
  changed one transfers gzip-compressed.
- **Old launchers keep working unchanged** (no forced migration, no broken updates).

## Non-goals

- Byte-range (partial-file) HTTP resume. File-level skip is the 99% win for a 12k-file
  pack of mostly-small files; nginx supports `Range` (verified) so this can be added later.
- Full-pack reconciliation against the index on every launch (too much I/O). Resume
  operates on the changelog-derived candidate window only.
- Changing the changelog bucket format or the existing MD5 index.

## Decisions (locked, per review)

| # | Decision |
|---|----------|
| Backward compatibility | **Changelog buckets stay exactly as today** (`{ts:{path:0\|1}}`); old clients are unaffected. |
| Server diff key | **Keep MD5** (`incremental/indexes/<pack>.json` unchanged) → **no migration / no mass re-add**. |
| Verification hash | **Add SHA-256 (hex)** as an **optional** top-level `"sha256"` map: `{ "<relpath>": "<sha256hex>" }`, carrying hashes for **changed files only** (accumulated over updates) — not a full-pack dump. |
| Files without a hash | **Not checked.** Base files come from `InitialDownloader`'s full-zip install (already validated); only changed files carry a hash. An `ADD` with no hash is downloaded as before (no skip, no verify). |
| Old-client safety | Old clients drop the non-numeric `"sha256"` key via `toLongOrNull`; Gson yields null for its unknown-enum values (no throw). Verified against the current parser. |
| In-run retry | **Yes** — failed files are retried up to **2** extra passes before throwing. |
| Parallelism default | `Runtime.getRuntime().availableProcessors()` clamped to `1..32`. |
| Changelog 304 | Client persists the changelog `ETag` + cached body per pack and sends `If-None-Match`; on `304` it re-parses the cached body. No server change (nginx already validates conditional GETs). |
| Changelog gzip | Client installs ktor `ContentEncoding(gzip)`; the host enables nginx `gzip` for `application/json` (ops, documented). Harmless if absent; mod files excluded (already compressed). |
| Scope | Client + settings + **server script**, all in this work; nginx gzip is a documented ops step. |

## Server — `GamesGlitchlessStatic/scripts/update-maker.py`

Single file; no CI change. Served content is regenerated by the existing CI on next push.

1. **Index/diff stays MD5.** `checksum_file` keeps `hashlib.md5` for the index used by
   `diff_index`, so only genuinely-changed files are bucketed (no migration bucket).
2. **Compute SHA-256 too, in the same single file read** (one `open()`, feed bytes to both
   an `md5` and a `sha256` digest) — avoids reading every file twice.
3. **Maintain an optional flat `"sha256"` top-level map** `{ "<relpath>": "<sha256hex>" }`
   (same pack-relative keys as the buckets, leading `/`). It is **carried in the changelog
   and updated per run**: set the hash for each `ADD` in this run's diff, drop the entry for
   each `REMOVE`. So it accumulates SHA-256 for files changed since the feature shipped and
   stays proportional to churn — it is **not** a full-pack dump. Files predating the feature
   simply have no entry (they are base files validated by the initial install).
4. **Buckets are untouched** — still `{ "<ts>": { "/path": 0|1 } }`. The map MUST stay flat
   (`{relpath: hexstring}`); old clients parse the changelog as `Map<String,Map<String,Action>>`
   and read the string hashes as null enums (no throw) before dropping the non-numeric
   `"sha256"` key. A nested value would make Gson throw — keep it flat.
5. All five packs flow through the same function and gain the optional map when regenerated.

Resulting changelog shape (the `"sha256"` map holds only changed files, not all 12k):
```json
{
  "1657214301": { "/config/AFSU.cfg": 1, "...": 1 },
  "1768066585": { "/some/removed": 0, "/config/AFSU.cfg": 1 },
  "sha256": { "/config/AFSU.cfg": "<hex of current version>" }
}
```

## Client — `TechnoparkLauncher`

### Changelog fetch: conditional GET (304) + gzip

The changelog is fetched every launch; most launches it is unchanged. Two optimizations:

- **Conditional GET → 304.** Persist per pack the changelog `ETag` (new
  `DownloadedInfo.changelogEtag: String?`) and cache the raw body to
  `<workingDir>/technomine/cache/<modpackKey>_changelog.json`. On `init()`, send
  `If-None-Match: <etag>`:
  - `304 Not Modified` → read the cached body and parse it (no body transferred).
  - `200` → use and re-cache the new body, store the new `ETag`.
  - no stored etag / no cache / any error → plain full GET (today's behavior).
  The body is **re-parsed** every launch against the current `lastUpdate` (which may have
  advanced since the body was cached), so a 304 still yields the correct (often empty)
  change set. `HttpDownloader` gains a conditional GET that returns `(status, etag, body?)`.
  No server change — nginx already emits `ETag`/`Last-Modified` and answers conditional GETs.
- **gzip.** Install ktor `ContentEncoding { gzip(); deflate() }` on the client so it sends
  `Accept-Encoding` and transparently decodes compressed responses. Enabling it server-side
  is an **ops step on the host** (not in either repo): in the nginx vhost,
  `gzip on; gzip_types application/json; gzip_min_length 1024;` (do **not** gzip the mod
  `.jar/.zip` files — already compressed). The client change is harmless if the server does
  not compress.

Combined: an unchanged launch transfers ~0 bytes (304); a changed launch transfers a
gzipped body.

### Changelog model (backward compatible)

`IncrementalDownloadLogic.kt`: replace the single-shot `fromJson<Map<String,Map<String,Action>>>`
with a small parse that walks the JSON object:
- numeric top-level keys → action buckets (path → `Action`), exactly as today.
- the optional `"sha256"` key → a `Map<String, String>` (relpath → hex), defaulting to
  empty when absent.

`ParsedChangeLog` gains `hashes: Map<String, String>` alongside `changes` and
`lastTimestamp`. When `hashes` is empty (old-format pack, or server not yet updated), the
flow degrades to today's behavior (download everything, no skip/verify) — fully compatible.

### Hash-skip = resume

Two steps keep the plan pure and isolate disk I/O:

1. **`buildDownloadPlan` stays pure** (path-traversal guard + split into delete/download),
   unchanged in signature. `REMOVE` → deletion; `ADD` → `(relativeKey, destFile)`.
2. **A new parallel skip step** (`filterUpToDate`, bounded by the parallelism setting,
   behind a `"Проверка файлов…"` progress phase) drops entries already correct, using the
   expected hash from `hashes[relpath]`:
   - expected hash present, local file exists, `file.sha256Hex()` **matches** → **skip**.
   - expected hash present, file missing or mismatched → keep (download).
   - **expected hash absent → keep (download), but do NOT hash and do NOT verify.** These are
     base files from the initial full-zip install (already validated) or old-format packs;
     the incremental flow only checks files it has a hash for.

Only files that have an expected hash *and* already exist on disk are hashed, so the skip
cost is proportional to the changed-file set, never the whole pack. Pure plan is tested
without I/O; the skip step against real temp files.

### Post-download verification

After `downloadToFile`, if an expected `sha256` is known, recompute the file's hash and
treat a mismatch as a failure for that item (so it is retried/reported). Guards against
silent corruption and makes the skip decision trustworthy.

### In-run retry & convergence

`download()` keeps aggregate-and-throw on terminal failure (do not launch a half-applied
pack), but first **retries the failed subset up to 2 more times** within the same run.
Because hash-skip means successful files are not redownloaded, each pass only re-attempts
what's still wrong. The timestamp advances only on full success; a still-incomplete run
leaves on-disk progress that the next launch cheaply skips → guaranteed forward progress.

### New hash helper

`File.sha256Hex(): String` (hex) added next to the existing `generateSHA256` (base64) /
`hashSHA1` helpers, using commons-codec `DigestUtils.sha256Hex` (already a dependency).

### Settings — parallel downloads

- `Settings.parallelDownloads: Int`, stored under key `parallelDownloads`, lazy default
  via `SettingsDefault.getDefaultParallelDownloads()` = `availableProcessors().coerceIn(1,32)`,
  clamp-on-write, copied in the `Settings` copy-constructor (mirrors `heapSize`).
  Backward compatible: missing key → default (0 sentinel → lazy default).
- UI: a numeric `TpField`/`TpTextField` row in `SettingsWindow.kt`, `parallelDownloads`
  state + `onParallelDownloadsChange` + `apply()` write-back in `SettingsViewModel.kt`,
  Russian label in `Strings.kt`.
- `IncrementalDownloader.download()` and the parallel hasher read
  `ConfigHelper.config.settings.parallelDownloads` instead of the `DOWNLOAD_PARALLELISM`
  constant (the `require(parallelism >= 1)` guard is satisfied by the clamp).

## Rollout

No ordering constraint and no breakage either way:
- **Old launchers** ignore the `"sha256"` key and behave exactly as before.
- **New launchers** read the optional map when present and gain skip/verify/resume; when
  it is absent (pack not yet regenerated) they behave as before.
- Deploy the two repos in any order. Resume/verify becomes active for a pack once both the
  new launcher is installed and that pack's changelog has been regenerated with `"sha256"`.

## Testing

Pure/testable units (no network, no globals), extending `IncrementalDownloadLogicTest`:
- `sha256Hex(File)` over known content.
- changelog parse: numeric buckets parsed as before; optional `"sha256"` map read when
  present and empty when absent; an old (no-`sha256`) changelog still yields the right
  changes with empty hashes.
- skip step over real temp files: skip when hash matches, keep when missing/mismatched,
  keep (no hashing) when expected hash absent.
- post-download verify: matching hash passes, mismatch becomes a failure.
- in-run retry: a file that fails then succeeds is not reported; a persistently failing
  file is reported after the retries.
- conditional changelog GET (MockEngine in `HttpDownloaderTest`): a `304` yields no body
  (caller uses the cache); a `200` returns body + new `ETag`; an `If-None-Match` header is
  sent when an etag is supplied.
- settings: `parallelDownloads` round-trips under its key and defaults when absent
  (mirror the `enableLogView` compat tests).

Server: a small round-trip check of `update-maker.py` (run on a tmp dir; assert buckets
keep the `0|1` shape, MD5 index is unchanged in form, and a `"sha256"` full map is emitted
with hex values), or a documented manual verification if no Python harness fits.

## Risks

- **Changelog size.** Directly mitigated: 304 means unchanged launches transfer ~nothing,
  and gzip shrinks the body ~5–10× when it does change. The `"sha256"` map carries only
  changed-file hashes (churn-proportional), so growth is slow. A separate
  `incremental/indexes/<pack>_sha256.json` remains a fallback if it ever matters.
- **Double hashing on the CI box.** Each file is hashed with MD5 + SHA-256 per run; done in
  a single read, so it's one extra digest, not an extra read.
- **Client hashing cost is bounded by churn.** Only changed files that already exist locally
  are hashed (base files have no expected hash and are never hashed), so the verification
  phase stays cheap even for GTNH.
